## 五、新发现（与现有文档的偏差）

### 5.1 【关键】`processDesign/save` 是 UPSERT 而非 INSERT

AGENTS.md §5.3 / docs/api.md 均未明确 `save` 是 UPSERT（以 `name` 为唯一键）。

**实测**：
- reset 后 design 表仅 1 行 id=9（seed stub）
- 多次 save（不同 name）复用 id=9，name 字段被覆盖
- 多次 deploy 复用 processDefineId=113，name 也被覆盖

→ 后续测试 runner 必须每次记录 processDefineId，不能依赖历史 id。

### 5.2 【新增字段】`activeTaskList`（detail 响应）

`processInstance/detail` 响应**除 `tasks[]` 外还包含 `activeTaskList[]`**，仅列出 taskState=10 的活跃任务：

```json
{
  "activeTaskList": [
    {
      "id": "91757302983157",
      "processInstanceId": "...",
      "taskName": "task1",
      "taskState": 10,
      "operator": "",
      "taskActorIdList": ["leader"],
      "formKey": "leave-form",
      ...
    }
  ]
}
```

→ `flows/README.md` / `docs/api.md` 缺该字段说明；测试 runner 可直接读 `activeTaskList` 取活跃 taskId，**不必全表扫描 `tasks[]` 找 taskState=10**。

### 5.3 【新增字段】`taskActorIdList`（detail.tasks[].taskActorIdList）

每个 task 对象包含 `taskActorIdList: ["leader"]` 数组（候选执行人列表），即使 `operator=""`（尚未指派）也存在。

→ runner 应优先用 `taskActorIdList` 判断 task 可执行人，而非依赖 JSON 设计时的 `assignee`。

### 5.4 【次要】`processInstance/startAndExecute` 不强制要求所有 task 的 assignees

实测只传 `assignees: {apply: "applicant"}`，task1/task2/task3 仍能正常流转（每个 task 各自的 `assignee` 字段已写死在 JSON 中：`leader`/`manager`/`boss`）。

→ runner 只需确保每个 task 提交时 `operator` 与 taskActorIdList 中某项匹配即可，**不必每个 task 都在 assignees 里写**。
