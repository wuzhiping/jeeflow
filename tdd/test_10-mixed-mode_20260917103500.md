## 3. 实测详情

### 3.1 Fork-Join 并行（A 模式，finalAmount=3000 nested）

```
apply    → user1    DONE  (fork1 自动触发两条 task)
task2    → checker  DOING (并行)
task3    → reviewer DOING (并行)
```

task2 + task3 都 agree 后：
```
state=10 activeTasks=1
taskName=task4 state=10 actor=  ← ❌ 应到 end 才对
```

### 3.2 根因（与 03-decision-expr 同源）

`engine._evaluate_decision` 评估 expr 时用 `vars_.get(key)`，但 `vars_` 是 `start_process_instance_by_id` 的 `{**(args or {})}`：
- facade._startAndExecute 的 flow_args 含 `"variables": {"finalAmount": 3000}`（嵌套）
- vars_ = `{"variables": {"finalAmount": 3000}, "assignees": "user1", ...}`
- 决策 expr `finalAmount > 5000` → `vars_.get("finalAmount")` → None → False
- e8 和 e9 都 False → fallback `edges[0]` = e8 → task4 (boss)

### 3.3 修正写法（C 模式，finalAmount 顶层）

```json
{
  "processDefineId": "113",
  "operator": "user1",
  "assignees": "user1",
  "title": "10-mix-3k-tl",
  "finalAmount": 3000
}
```

实测：
```
state=20 activeTasks=0
apply/task2/task3 全 state=20
task4 未创建 ← 决策正确走 e9 → end
```

## 4. 关键发现

### 4.1 业务变量 placement 规则（再次确认）

| 写法 | 决策 expr 是否能取到 |
|---|---|
| `variables: {finalAmount: 3000}` | ❌ 嵌套在 vars_["variables"] 里 |
| `finalAmount: 3000` (顶层) | ✅ vars_["finalAmount"] |
| `f_finalAmount: 3000` (顶层) | ✅ vars_["f_finalAmount"]，但 expr 要写 `f_finalAmount>5000` |

**约定**：业务变量（决策 expr 引用的 key）必须放 `startAndExecute` 顶层 dict。

### 4.2 fallback 顺序（决策 expr 全 False 时）

```python
# engine.py:366-375
for edge in edges:                       # 1. 找第一条无 expr 的边
    expr = edge.properties.get("expr", "")
    if not expr:
        return _execute_node(target)
if edges:                                  # 2. 找第一条边
    return _execute_node(edges[0].target)
```

10-mixed-mode 的 e8 和 e9 都有 expr，当 expr 全 False 时回退到 `edges[0] = e8` → task4。

### 4.3 taskType=1 行为

task3 `taskType=1`（标记为「其他类型 task」）：
- 正常创建 task（state=10 DOING）
- 正常通过 execute 完成（state=20 DONE）
- 不影响流程行为（仅前端展示分类）

### 4.4 preInterceptors / postInterceptors

JSON 顶层两个字段都是空字符串 `""`：
- 引擎对空字符串**不触发任何拦截器**（无注册副作用）
- 测试流程无拦截器副作用
