## 1. 流程结构（7 节点 / 7 边）

```
start → apply(applicant) → fork1
                            ├─ e2 → taskA(userA, taskType=0) → e4 → join1
                            └─ e3 → taskB(userB, taskType=1) → e5 → join1
                                                          → e6 → end
```

**关键属性**：
- `fork1` (snaker:fork)：并行分流，激活所有出边的 task
- `taskB` `taskType=1`（副审/旁审）— 实测 detail 显示 0，引擎可能不区分
- `join1` (snaker:join)：汇合，等待所有进入边的 task 完成才触发下一节点

`tasks` 全表：

### 2.3 join 等待验证

**仅完成 taskA** 后：


taskB 仍 active，state 仍 10（DOING），join1 未触发 → ✅ join 正确等待所有 fork 分支。

### 2.4 完成 taskB → join 触发

```json

```

state=20 DONE，join1 触发 → end → 流程完成 → ✅ join 汇合正确。

## 5. 引擎行为总结

| 行为 | 实测 |
|---|---|
| fork 同时激活所有出边 task | ✅ taskA + taskB 同时 active |
| join 等待所有 fork 分支完成 | ✅ taskA 完成后 taskB 仍 active |
| join 全部完成触发下一节点 | ✅ taskB 完成后 join1 触发 end |
| taskType=1 (副审) 与 0 (主审) 区别 | ⚠️ detail 全部显示 0，引擎不区分（待确认） |
| 并行 task 共享同一 approvalRecord 顺序 | ✅ 按 task 完成先后排列 |

## 6. 已知保留行为（不影响功能）

- `historyNodeNames` 缺 `start`（与 02-multi-task 一致）
- `historyEdgeNames` 缺 `e5`（taskB→join1）— 推测并行汇合时只取首条完成路径，与 02 multi-task 的 design/define 边索引类似
- `taskB` JSON `taskType=1` 但 detail 显示 0 — 引擎可能未实现 taskType 区分（或仅作为字段持久化不参与状态机）
