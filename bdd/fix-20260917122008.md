## 2. 7 大错误模式 + 修复方法

### 错误 1：decision expr 字符串值比较

**症状 A（expr 用字符串）**：
```json
{"properties": {"expr": "f_category==travel"}}  // ← expr 是字符串
```
- 引擎 regex 不匹配 → 返回 False → 所有分支走首边（兜底）
- 走错分支，业务语义错误

**症状 B（expr 是数字但 value 是字符串）**：
- startAndExecute 传 `f_category="travel"`（字符串），expr `f_category==1`
- regex 匹配后 `actual = float("travel")` **抛 ValueError**
- startAndExecute 返回 `code=99999999, msg="could not convert string to float: 'travel'"` —— **流程直接失败，未创建实例**

**根因**：`main.py:43-61 SimpleExprEvaluator` regex 限定数字，且 float() 转换未捕获异常

**修复方法**：
- **expr + value 必须都是数字**：`expr="f_category==1"` + `variables.f_category=1`
- 不要写 `f_status==approved`，应写 `f_status==1`
- 前端 form 应将枚举值映射到数字（form 层处理）

**示例（Task 7）**：
```python
# 错误 A: expr 字符串
"expr": "f_category==travel"

# 错误 B: value 字符串
"variables": {"f_category": "travel"}

# 正确: 数字编码
"expr": "f_category==1"
"variables": {"f_category": 1}
```

**TDD 自检**：
- startAndExecute 的 `variables.f_xxx` 是 JSON int/float，不是字符串
- expr 中所有操作数都是数字
- 字符串值场景测试：传字符串应预期走首边（regex 不匹配）或修正为数字

### 错误 2：handler FQCN 臆造

**症状**：
- 节点配 `assignmentHandler="jeeflow.assignment.TaskRoleAssigneeHandler"`（臆造的）
- handler 找不到 → `_resolve_actors` 返回 `[]` → `_create_task` `if not actors: return` 静默跳过
- 流程卡死 state=10，active=0，无任何日志

**根因**：4 个内置 handler 都有**精确 FQCN**，且 TaskRole/DeptLeader 用 `$`（内部类分隔符）而非 `.`

**修复方法**：严格对照下表复制 FQCN：

| handler | 正确 FQCN |
|---|---|
| Operator | `com.mldong.jeeflow.interceptor.impl.OperatorAssignmentHandler` |
| FormField | `com.mldong.jeeflow.interceptor.impl.FormFieldAssigneeHandler` |
| DeptLeader | `com.mldong.jeeflow.interceptor.impl.OrgUserAssignmentHandlers$DeptLeaderAssignmentHandler` |
| DeptMainLeader | `com.mldong.jeeflow.interceptor.impl.OrgUserAssignmentHandlers$DeptMainLeaderAssignmentHandler` |
| ApplicantDeptLeader | `com.mldong.jeeflow.interceptor.impl.OrgUserAssignmentHandlers$ApplicantDeptLeaderAssignmentHandler` |
| ApplicantDeptMainLeader | `com.mldong.jeeflow.interceptor.impl.OrgUserAssignmentHandlers$ApplicantDeptMainLeaderAssignmentHandler` |
| TaskRole | `com.mldong.jeeflow.interceptor.impl.OrgUserAssignmentHandlers$TaskRoleAssigneeHandler` |

**TDD 自检**：节点配 handler 后，`processInstance/detail` 检查 `activeTaskList` 是否创建；为空 + state=10 → FQCN 错。

**详细**：见 `docs/known-issues.md §25`

### 错误 3：TaskRole handler 节点 id 不在 SPI

**症状**：
- 节点 id `finance_review`，SPI `DEMO_ROLE_TO_USERS.json` 无 `finance_review` 键
- handler `find_by_role("finance_review")` → `[]` → 同错误 2 静默跳过

**根因**：TaskRoleAssigneeHandler 用 `node.id` 查 SPI role_code

**修复方法**：
- 选项 A：改节点 id 为已有 SPI role_code（如 `finance`、`boss_audit`）
- 选项 B：在 `./spi/demo/DEMO_ROLE_TO_USERS.json` 添加新键 `"<node.id>": ["<userId>"]` 并 human 重启服务

**示例（Task 7）**：
```json
// 错误: 节点 id = "finance_review"，SPI 无此 key
{"id": "finance_review", ...}

// 修复 A: 改 id
{"id": "finance", ...}  // SPI 已有 "finance": ["leader", "manager"]

// 修复 B: 加 SPI
// ./spi/demo/DEMO_ROLE_TO_USERS.json
{"finance_review": ["manager"]}
```

**注意**：SPI JSON 修改后必须 human 重启服务（`data.py` 模块级 dict 启动时一次性加载）

### 错误 4：handler 失败导致 fork 分支静默通过 ⚠️ 业务安全

**症状**：
- fork 三个分支 A/B/C，B 节点 handler 失败（actor=[]）
- A/C 完成 → join 检查 `find_doing_tasks=0` → 流转 end → state=20 DONE
- B 分支**从未真正审批**，业务上视为非法通过

**根因**：
- `engine.py:378-379` `_create_task` `if not actors: return` 静默
- `engine.py:334-335` fork `for n in _follow_edges(...)` 不检查子分支结果
- `engine.py:336-338` join `if not await self.repo.find_doing_tasks(...)` 只查 DOING task 数（handler 失败的分支根本没 task 创建）

**TDD 自检**：
- fork 流程必须检查每个分支的 `activeTaskList` 是否含对应 task
- `highLight.historyNodeNames` 含节点 ≠ 该节点 task 一定创建（history 只记访问）

**修复方法**：
- 设计：handler 节点 id 必须匹配 SPI（见错误 3）
- 设计：关键审批节点优先用 `assignee="<user>"` 而非 handler
- 引擎层建议：handler 失败时记 warning 日志；fork 应跟踪"未激活分支"，join 检查失败

**详细**：见 `docs/known-issues.md §26`

**示例（Task 10）**：
```json
// 错误: finance_approval handler 失败但 join 仍流转
{"id": "finance_approval", "assignmentHandler": "..."}

// 修复: 改 id 为 SPI 已有
{"id": "finance"}
```

### 错误 5：FormField handler 字段名错配

**症状**：
- 节点 `pm_form` 配 `field.f_pm_reviewer="user1"`（期望字段名）
- handler 查 `f_<node.id>` = `f_pm_form` → 找不到 → `[]` → 流程卡死

**根因**：`builtin.py:55` `_find_field_value` 用 `node.id` 拼字段名

**修复方法**：
- 字段名必须 = `f_<node.id>`（注意是 `f_<node.id>` 而非任意字段名）
- `startAndExecute.variables` 顶层必须传该字段

**示例（Task 5/11）**：
```json
// 错误: 字段名错配
{"id": "pm_form", "field": {"f_pm_reviewer": "user1"}}
// 启动时: {variables: {f_pm_reviewer: "user1"}}  ← handler 查 f_pm_form 找不到

// 正确
{"id": "pm_form", "field": {"f_pm_form": "user1"}}
// 启动时: {variables: {f_pm_form: "user1"}}  ← handler 查 f_pm_form 命中
```

**TDD 自检**：FormField handler 节点的 field 字段名 = `f_<node.id>`；startAndExecute 顶层 variables 必须包含该字段

**详细**：见 `docs/known-issues.md §24`

### 错误 6：candidateUsers/candidateGroups 不解析 actor

**症状**：
- 节点配 `candidateUsers="userB,userC"`（仅 candidatePage 用）
- `_resolve_actors` 不读 candidateUsers → `actors=[]` → 流程卡死

**根因**：`engine.py:415-451 _resolve_actors` 仅解析 assignee / assignmentHandler / KEY_NEXT_NODE_OPERATOR

**修复方法**：
- candidateUsers/candidateGroups **必须配合 assignee 或 handler**
- 单 actor 模式：`assignee="userB"`
- 多 actor 单 task：`assignee="userB,userC"`（任一可办）
- 多 actor 会签：`assignee="userB,userC"` + `performType=1, countersignType=PARALLEL/SEQUENTIAL`

**示例（Task 14）**：
```json
// 错误: 只有 candidateUsers
{"candidateUsers": "userB,userC"}

// 正确: 同时配 assignee
{"assignee": "userB,userC", "candidateUsers": "userB,userC"}
```

**注意**：candidateUsers/candidateGroups 仅影响 `processTask/candidatePage` 查询接口，**不影响 task 执行**。详情见 `docs/known-issues.md §22`

### 错误 7：多入边 task 节点重复创建 ⚠️ 业务重复

**症状**：
- task 节点有 N 个入边
- 每次前驱激活时 `_execute_node` 触发 → 创建新 task
- 同一节点被创建 N 个 task，需各执行一次才能流转

**根因**：`engine.py:80-82` + `_execute_node` 在每次节点被前驱激活时都创建新 task

**修复方法**：
- **设计**：避免多入边汇合到 task 节点；改用 join 节点合并后再到 task
- **设计**：使用线性流（`01-simple` 风格），避免 fan-in
- **引擎层**：节点首次创建 task 后，后续入边激活应跳过创建，仅检查已有 task 状态

**示例（Task 15）**：
```json
// 错误: hr_review 有 2 个入边
{"id": "hr_review", "edges_in": ["from_dept_approve", "to_dept_approve"]}

// 修复: 用 join 合并
{"id": "join_approve", "type": "snaker:join"},
{"id": "hr_review", "edges_in": ["join_approve"]}  // 仅 1 个入边
```

**TDD 自检**：fan-in 节点在 detail 中检查 task 数量是否 = 入边数；若是，需逐个执行

**详细**：见 `docs/known-issues.md §27`
