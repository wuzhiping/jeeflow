# BDD #129 PARALLEL 一票否决边界 (20260919 152000)

## 流程设计
```mermaid
flowchart LR
    start([开始]) --> apply[申请 user1]
    apply --> veto_review[会签 userA,userB,userC<br/>PARALLEL + ONE_VOTE_VETO]
    veto_review --> end([结束])
```

## 场景
3 人 PARALLEL 会签 + ONE_VOTE_VETO 一票否决配置。

## 测试用例

| Case | userA | userB | userC | 期望 | 实测 state | 结论 |
|------|-------|-------|-------|------|------------|------|
| 1 (REJECT) | 20(REJECT) | - | - | state=45 (REJECT) | state=20 (DONE) | ⚠️ BUG |
| 2 (AGREE) | 1(AGREE) | 1(AGREE) | 1(AGREE) | state=20 (DONE) | state=20 | ✅ |
| 3 (PARTIAL) | 1 | 20 | - | state=45 | (未测) | - |

## 🚨 BUG 发现

### Bug-1: REJECT 时 state=20 而不是 state=45

`veto_review` 节点配置 `countersignDisagree=20` + ONE_VOTE_VETO 期望触发 REJECT 路径
（state=45 / REJECTED）。但实测 userA REJECT 后 state 直接到 20（DONE），
其他 userB/userC 任务被 mark 为 99 (ABANDON)。

**预期行为**：
- ONE_VOTE_VETO 命中时，触发 `submitType=20` (REJECT) 走 reject 边
- instance state 应该转 45 (REJECTED)，或显式拒绝流程

**实测行为**：
- state 直接 20 (DONE)
- userB/userC 任务变 99 (ABANDON) — 不算干净

**根因**：`engine.execute_process_task` 收到 `submitType=20` 时只走 facade
`_processTask_execute` 的 REJECT 分支（`execute_and_jump_to_end`），但
**会签聚合 task** 走的是单 task execute（不是并行聚合），所以 REJECT 直接结束流程。

修复方向（待评估）：会签 + ONE_VOTE_VETO + REJECT 时，应走 reject 边（流程设计需有 reject 出边），
否则按当前实现就是直接结束（state=20）。

### Bug-2: 投票结束后剩 userC 任务在 todoList 之外

`veto_review` PARALLEL + 全员通过时，最后一个 user 通过后：
- userA userB 的 task 已经 state=20 (DONE)
- userC task 仍 state=10 (DOING) — 但 todoList 不会列出 userC

实测用 `taskId=91869608614925` 直接调 `processTask/execute` userC 是可用的，
但 `processTask/todoList` 不列出。说明 actorIds 计算逻辑没把 userC 当作当前 actor。

可能是 §55 已知 BUG（doneList actorIdList=None）的某种回归。

## 结果
- memory (8101): ⚠️ REJECT 行为不符预期 / ✅ AGREE 正常
- pg (8102): ⏭️ 暂未跑

## 改进建议
- engine.execute_process_task: REJECT 路径不直接 end 流程；如有 reject 边则走 reject
- facade._processTask_execute: ONE_VOTE_VETO REJECT 时记录事件
- todoList: 修 actorIds 计算 bug
