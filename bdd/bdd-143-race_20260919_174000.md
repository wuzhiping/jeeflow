# BDD #143 高并发 startAndExecute race condition (20260919 174000)

## 测试场景
- 20 个并发请求 startAndExecute 同一 processDefineId
- 期望：20 个独立 instance，IDs 唯一，状态一致

## 测试结果（memory 后端 8101）

| 维度 | 期望 | 实测 |
|------|------|------|
| 总请求数 | 20 | 20 |
| 成功数 | 20 | 20 (100%) |
| 唯一 instanceId | 20 | **20 ✓** |
| 失败数 | 0 | 0 |
| 总耗时 | < 5s | 1.42s |
| 状态一致 (completed=20) | yes | yes |

**IDs 示例**（相邻间隔均匀 ~3074ms 雪花）：
- 91871396867085, 91871396871183, 91871396875281, ...
- 91871396919337, 91871396922411, ...

## 结论
- Memory 后端：asyncio 协程模型天然串行化（无 race condition）
- 所有 instance IDs 唯一，状态正确（completed=20）
- 1.42s 完成 20 个并发 = 70ms/请求（合理）

## 推测 PG 后端行为
- `with_tx` 事务 + `lock_instance_for_update` 悲观锁保证串行
- 但 facade `_startAndExecute` 仅对 `_engine.start_process_instance_by_id` 包了 with_tx
- 后续 `_engine.execute_process_task`（auto-complete apply task）**未包事务**
- 高并发时同 instance 的 task 创建可能重复

**未验证**：PG 后端（8102 未启）

## 风险点（PG 后端）
1. 同一 instance 在 1 个 with_tx 内创建 OK
2. startAndExecute 自动完成 apply task 时再次进 _create_task
3. _create_task 会再次 lock_instance_for_update（需要新事务）
4. 如果第二次 lock 在新事务里，第一次 with_tx 已结束 → 可能 race

## 建议（FIX-T43）
- `facade._startAndExecute` 整个方法包一个 with_tx
- 包含 start_instance + auto_complete apply task
- 保证同 instance 全程持锁
