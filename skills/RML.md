───────────────────────────────────────────────────────────
角色 1 · 引擎开发者 (Engine Developer) — bro
───────────────────────────────────────────────────────────

【定位】
  定义场本身. 修改 vendor/jeeflow/ + 维护 docs/ + FIX 编号.

【产出】
  vendor/jeeflow/*.py  |  docs/*.md  |  FIX-Tnnn  |  statics.json

【核心技能】
  • Python (Snaker 引擎改写)
  • 工作流原理 (state machine / transition / 节点语义)
  • 27 个历史 BUG + 已知限制 (§30-§46)
  • W0XX 系列 verify 规则设计 (W012 已用于 BUG-1)
  • SimpleExprEvaluator 正则 (expr 解析约束)
  • AGENTS.md 文档工程 (3 角色协作指南)
  • BDD/P0/P1/Phase2 全量回归测试

【产出物】
  vendor/jeeflow/engine.py       — 引擎核心
  docs/BUGS.md                   — 已知问题库 (FIX-T1~T112)
  docs/AGENTS.md                 — 协作协议 (3 角色)
  docs/known-issues.md §1-§112   — 详细问题
  bdd/bdd-NNNN-*.sh             — BDD 验证脚本
  statics.json fix_total/bdd_total — 指标

───────────────────────────────────────────────────────────
角色 2 · 引擎测试 (Engine QA)
───────────────────────────────────────────────────────────

【定位】
  每次引擎改动后跑全量回归. 防止新 BUG, 验证修复.

【产出】
  bdd/*.sh + 测试报告 + BUG 复现脚本

【核心技能】
  • Shell 脚本 (BDD 跑全量)
  • pytest / BDD 框架
  • 边界条件扫描 (race condition / 并发 / 状态机)
  • BUG 复现报告 (现象 + 复现步骤 + 期望 vs 实际)
  • 性能基准 (P95 latency / 吞吐)
  • 数据库回归 (PG vs sqlite 行为一致性)

【产出物】
  bdd/bdd-1001-1060-p0-regression.sh        — P0 全量
  bdd/bdd-1065-1100-p1-regression.sh        — P1
  bdd/bdd-1101-1110-phase2.sh                — Phase 2
  bdd/bdd-1501-1503-fix-t110-task-multi-out — BUG-1 回归
  性能 baseline + 监控                       — SRE 联动

───────────────────────────────────────────────────────────
角色 3 · 流程开发者 / 流程设计师 (Process Designer) — hermes
───────────────────────────────────────────────────────────

【定位】
  用现成 API 设计业务流程. 不动引擎.

【产出】
  tdd/<name>.json → flows/<name>.json (晋升后)

【核心技能】(6 硬规则)
  • 读文档 5 分钟: AGENTS.md §5.8 + flow.md §3.3-§3.4 + §5.7 + BUGS.md §30
  • 节点选型: task / decision / fork / join / custom / end (6 种)
  • 字段权限: PERMISSION_f_X (1=只读 / 2=编辑 / 3=隐藏)
  • 会签模式: PARALLEL / SEQUENTIAL / 比例 / 一票否决 (4 种)
  • 变量命名: f_* (发起) / tf_* (执行) / u_* (操作人)
  • submitType: 0=同意 / 2=拒绝 / 6=回退
  • 判 BUG 自检 3 步: 复现 + 文档 + 样例对比
  • 审计双输出: ndjson (运维 grep) + txt (bro 看)

【产出物】
  jeeflow-flows/*.json                       — 流程设计
  work_logs/0X_*.md                          — 跑通日志
  audit_txt/*.txt                            — 审计摘要
  insights/01_design_patterns.md             — 心得
  insights/02_bug_findings.md                — 引擎 BUG (经自检)
  insights/03_pitfalls.md                    — 设计错教训
  insights/04_engineer_feedback.md           — 给开发者反馈

【红线】(bro 三次纠正)
  ✅ 节点顺序 / assignee / 字段权限
  ❌ 不动 engine/handler/FIX 编号
  ❌ 不加 action
  ❌ 改 docs

───────────────────────────────────────────────────────────
角色 4 · 流程测试 (Process QA)
───────────────────────────────────────────────────────────

【定位】
  跑通流程 + 校验节点顺序 + 固化实例 ID.

【产出】
  tdd/test_<name>_<YYYYMMDDHHMMSS>.md + 实例固化

【核心技能】
  • curl 调 API (startAndExecute / execute / detail)
  • approvalRecord + highLight 校验 (节点顺序 / 高亮轨迹)
  • 字段权限试错 (让角色试着改, 看是否被拒)
  • 状态机跟踪 (state 10/20/45/99)
  • 异常分支覆盖 (驳回 / 回退 / 委托 / 跳过)
  • BUG-N 实例固化 (v1 BUG / v2 修复 对比)

【产出物】
  tdd/test_<name>_<timestamp>.md               — curl 脚本 + 请求/响应
  audit_logs/<define>_<instance>.ndjson        — 原始 API 证据
  audit_txt/<define>_<instance>.txt            — 摘要 (bro 看)
  实例 ID 列表 (固化, 复盘用)

───────────────────────────────────────────────────────────
角色 5 · 业务审批人 (Approver) — 流程的真正用户
───────────────────────────────────────────────────────────

【定位】
  流程真正跑起来的人. 大多数用户.

【产出】
  提交申请 / 审批同意/拒绝 (UI 操作)

【核心技能】
  • 会用 UI: 飞书/微信/Web 弹窗 → 看到待办 → 点同意/拒绝
  • 填字段: 必填项不漏, 上传附件
  • 看上下文: 谁申请 / 什么事 / 历史审批
  • 委托: 出差时委托他人审批 (delegation)
  • 紧急回退: 流程错了, 知道回退到哪一步 (submitType=6)

【培训重点】
  • 不会写代码, 不能让他们学 JSON
  • UI 必须自适应: 不同流程显示不同字段
  • 通知必须触达: 飞书 + 微信 + ntfy 多通道

───────────────────────────────────────────────────────────
角色 6 · 架构师 / EA (Enterprise Architect) — SCAMPER "合"
───────────────────────────────────────────────────────────

【定位】
  jeeflow 在企业架构大图的定位. 选型决策.

【产出】
  企业级流程架构图 + jeeflow 在大图的定位

【核心技能】
  • 企业架构 (TOGAF / Zachman)
  • jeeflow vs Camunda vs Flowable vs Activiti 选型
  • 跟 ERP (SAP / Oracle) / OA (钉钉/企业微信) 集成
  • L0-L4 流程分层 (战略/战术/操作/执行)
  • RACI (谁负责 / 谁审批 / 谁咨询 / 谁通知)

【产出物】
  流程大图 (FDE 视角: 业务域 × 流程域 × 能力域)
  jeeflow 集成规范 (跟其他系统的对接协议)
  选型决策树

【什么时候需要】
  • 5 个部门以上用 jeeflow
  • 跟外部系统集成 (财务 / HR / 供应链)
  • 安全审计要求

角色 7 · SRE / 运维 (Site Reliability)
───────────────────────────────────────────────────────────

【定位】
  监控 + 告警 + 复盘 + 容量规划.

【产出】
  监控面板 + 告警规则 + 复盘报告

【核心技能】
  • PG / sqlite 性能调优
  • cron 监控 (jeeflow_log_summary 就是)
  • 错误码归类 (code: 0 / 99999999 / 500)
  • 灰度发布 / 回滚策略
  • trace_id 全链路追踪
  • 容量规划 (实例数 / 用户数 / QPS)

【产出物】
  监控面板 (Grafana)
  告警规则 (state=10 超过 X 分钟 / 500 错误率 > Y%)
  复盘报告 (每次事故)
  性能 baseline

   ↓ webhook + 适配器

   ↓ 季度报告
架构(按需): 架构师 (角色6)
   ↓ 选型 + 集成规划
