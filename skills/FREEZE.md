## 3. 为什么冻结

### 3.1 三个问题

回看 RML.md 与 `docs/AGENTS.md`, 我们注意到三个信号:

**信号 1 · 我们不知道"客户要什么"**
- 当前 `flows/*.json` 共 19 个, 多为"测试引擎能力" 而非"真实业务"
- `tdd/` `bdd/` 多数为引擎边界场景, 不是客户痛点
- RML §6 建议"未来招人" 也是以"工程团队扩编"为中心, 不是以"客户增长"为中心

**信号 2 · 反馈链路断了**
- `skills/users.md` 只描述"如何问客户", 但**没有**说"问完怎么办"
- 没有 SLA / 复盘 / 改进 / 通知客户的闭环
- 客户的 bug 报告落入 `tdd/` 后, 工程师修复, 客户不知道结果

**信号 3 · 制度空缺**
- 没有"客户旅程图"
- 没有"客户成功指标"
- 没有"客户优先排序"
- 路线图 / TODO / SLA 全是工程视角

### 3.2 不冻结的风险

| 风险 | 后果 |
|------|------|
| 继续造功能 | 客户用不上, 浪费 |
| 继续修 BUG | 修复的 BUG 可能客户根本碰不到 |
| 继续写文档 | 文档可能客户不读 |
| 继续扩团队 | 团队结构与客户需求错位 |

### 3.3 冻结的好处

| 收益 | 体现 |
|------|------|
| 工程师时间回流客户 | 用 hermes 助理身份持续对话 flowuser |
| 文档从"自述"变"回应" | 客户问什么, 我们写什么 |
| 路线图从"工程想"变"客户要" | Phase 8 起, 客户主导 |
| 反馈闭环成为基础设施 | 所有后续改进都有据可循 |

## 4. 解冻条件

### 4.1 何时可以解冻

**必须同时满足**:

| # | 条件 | 验证方式 |
|---|------|----------|
| 1 | 至少 5 个真实客户的反馈闭环走完 | `skills/FEEDBACK.md` 案例 ≥ 5 |
| 2 | 客户旅程图 (至少 3 段) 已建立 | `skills/CUSTOMER.md` §3 |
| 3 | 客户视角路线图 ≥ 3 个阶段已规划 | `skills/ROADMAP.md` §3 |
| 4 | 反馈 SLA 指标 (响应时间 / 闭环率 / 客户满意度) 已有基线 | `skills/FEEDBACK.md` §6 |
| 5 | 至少 1 个 BUG 经反馈闭环被修复并通知客户 | `docs/BUGS.md` 闭环标记 |

### 4.2 解冻后做什么

解冻后**优先**做的事 (按客户反馈排序):
1. 修复被反馈最多的 BUG (按次数, 不按工程师判断)
2. 新增客户最常用的流程模式 (按请求次数)
3. 改进客户最痛点的文档 (按"读不懂"反馈)
4. 优化客户最卡的 UX (按"找不到入口"反馈)

### 4.3 解冻后**不**做什么
- 不再做"工程师想象的增强"
- 不再为"未来可能用" 的功能投入
- 不再为"对标 Camunda"等外部参照而做

## 6. 冻结期不可触碰的边界

### 6.1 一般边界

| 边界 | 含义 |
|------|------|
| 不动 raw data 目录 | `vendor/`, `main*.py`, `flows/`, `tdd/`, `bdd/`, `sla/`, `docs/`, `spi/`, `ui/`, 根 `*.md` |
| 不假设客户需求 | 所有需求从 `users.md` 对话或 `FEEDBACK.md` 案例中来 |
| 不引入新依赖 | `pyproject.toml` / `package.json` 不变 |
| 不做性能优化 | 无反馈驱动不做性能工作 |
| 不做架构重构 | 除非反馈明确指向架构缺陷 |

### 6.2 客户数据绝对不可触碰 (硬约束)

> ⚠️⚠️⚠️ **最高优先级约束** · 违反此条 = 不可挽回

| 约束 | 含义 |
|------|------|
| **绝不调用 `/api/reset`** | 一旦调用, 用户所有流程实例/任务/设计全部丢失, 不可恢复 |
| **绝不调用 `_reset_memory()`** | main.py:118 同等效果, 清空 repo._defines / _instances / _tasks / _actors / _cc / _designs / _designHis / _surrogates |
| **绝不建议 reset 操作** | 即使是测试场景, 也必须用本地实例 (`main.py` 8101 / `main_pg.py` 8102), 不能用用户实例 |
| **绝不在用户实例上做破坏性实验** | 用户实例 = 真实工作内容, 不是测试沙盒 |

**事实背景**:
- 用户与开发环境**不在同一台机器**
- 用户使用**内存版本**工作流引擎 (`https://abc.feg.cn/jeeflow/`)
- 内存版本**重启即丢数据**, 但我们绝不能加速这个过程
- 任何 `/api/reset` 操作会**立即**清空用户的真实工作

**正确做法**:
- 测试 / 验证用本地 `main.py` (8101) 或 `main_pg.py` (8102)
- BDD 套件使用本地实例 (sla/check_bdds_dual.sh)
- 用户数据**只读**, 即使是配合调试也要先备份 (无法备份因为内存, 所以**不能调试**)
- 用户反馈的 BUG 复现, 必须在**本地**完成, 不能在用户实例复现

**违反后果**:
- 用户数据全部丢失
- 信任崩塌, 客户永久离开
- jeeflow 私用定位失效

**审计**:
- 任何 reset 相关 API 调用必须事前双签 (hermes + bro)
- 调用后必须在 `skills/feedback/` 留档, 即使是本地实例
