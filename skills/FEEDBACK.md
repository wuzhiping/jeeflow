# FEEDBACK.md · 用户反馈闭环流程 (本轮核心交付)

> **目的**: 把"客户说一句"变成"客户看到改进".
> **范围**: 任何来源 (客户直说 / 流程 BUG / 文档不清 / UX 痛点) 的反馈.
> **核心思想**: 反馈不是噪音, 是系统的方向盘.

---

## 1. 一句话

**所有反馈进入同一个闭环, 5 步走完, 客户得到回应, 系统得到改进, 经验得到沉淀.**

---

## 2. 闭环全景 (5 步 + 1 反馈)

```
        ┌──────┐
        │ 客户 │  L1/L2/L3 任意客户
        └──┬───┘
           ↓ (1) 反馈触发
   ┌──────────────┐
   │  01 · 接收   │  接收 + 登记 + 编号 + 渠道
   └──────┬───────┘
          ↓ (2) 分流分类
   ┌──────────────┐
   │  02 · 分类   │  类型 / 优先级 / 归属
   └──────┬───────┘
          ↓ (3) 处理执行
   ┌──────────────┐
   │  03 · 处理   │  修复 / 改进 / 解释 / 转需求
   └──────┬───────┘
          ↓ (4) 验证确认
   ┌──────────────┐
   │  04 · 验证   │  内部验证 + 客户回访
   └──────┬───────┘
          ↓ (5) 闭环通知
   ┌──────────────┐
   │  05 · 通知   │  客户知道结果 + 经验沉淀
   └──────┬───────┘
          ↓
        ┌──────┐
        │ 客户 │  (继续对话 / 提新反馈)
        └──────┘
```

**关键原则**:
- 每一步都有产物
- 每一步都不漏
- 闭环通知**必须送达客户** (不是写日志就完事)

---

## 3. 五步详解

### 3.1 步骤 01 · 接收

**触发**: 客户发出反馈

**渠道** (按现状):
| 渠道 | 类型 | 接收人 | 当前状态 |
|------|------|--------|----------|
| hermes peer DM flowuser | 文字 + 审计 | hermes | 启用 (见 `skills/users.md`) |
| 客户邮件 | 文字 + 附件 | hermes | 待启用 |
| 飞书机器人 | 文字 + 图片 | AI 助理 | 规划中 |
| 客户支持工单 | 结构化 | 培训师 (+A) | 待招 |
| 引擎错误响应 | API code | SRE 自动 | 已启用 (code != 0) |
| tdd/ 中 BUG 复现 | json | 流程测试 | 已启用 |

**接收动作**:
1. 完整记录原文 (含上下文, 时间, 客户 ID)
2. 分配唯一反馈编号 `FB-NNNN`
3. 写入 `skills/feedback/inbox/FB-NNNN.json`

**编号规则**:
- 自 1 起递增, 不跳号, 不重复
- 格式: `FB-NNNN` (4 位数, 9999 之后 FB-10001)
- 编号作为后续所有追溯的 key

**反例**: 不要把"客户说流程很卡" 直接报修, 一定要先接收登记.

---

### 3.2 步骤 02 · 分类

**目标**: 让反馈找到正确的人.

**分类维度**:

| 维度 | 取值 | 谁判断 |
|------|------|--------|
| 类型 | bug / 改进 / 文档 / UX / 咨询 / 需求 | 接收人 |
| 优先级 | P0 / P1 / P2 / P3 | 接收人 (规则见下) |
| 归属 | engine / flow / doc / ui / spi / sla | 接收人 |
| 影响范围 | 单客户 / 多客户 / 全局 | 接收人 |
| 复现难度 | 易 / 中 / 难 | 接收人 |

**优先级规则**:

| 级别 | 条件 | SLA |
|------|------|-----|
| P0 | 流程走不通 · 数据错误 · 阻塞业务 | 24h 内首次响应, 7d 内闭环 |
| P1 | 体验差 · 文档不清 · 边缘 BUG | 3d 内首次响应, 30d 内闭环 |
| P2 | 改进建议 · 文档补充 · UX 优化 | 7d 内首次响应, 90d 内闭环或排期 |
| P3 | 闲聊 · 想法 · 远期需求 | 30d 内归档或转需求池 |

**分类产物**: 更新 `skills/feedback/inbox/FB-NNNN.json`, 添加分类字段.

**反例**: 不要把"客户问能不能加新节点类型"当 P0. 这是需求, 不是故障.

---

### 3.3 步骤 03 · 处理

**根据类型走不同子流程**:

```
                       FB-NNNN
                          │
        ┌────────┬────────┼────────┬────────┐
        ↓        ↓        ↓        ↓        ↓
       bug    improve    doc       UX    consult
        │        │        │        │        │
        ↓        ↓        ↓        ↓        ↓
     引擎开发   转需求池   文档更新  UI 建议  即时回复
     bro      (ROADMAP)  hermes   (UI 团队) hermes
```

#### 子流程 A · bug 处理

1. 复现: 用客户的实例 + 审计数据复现 (不靠记忆)
2. 定位: 在 `vendor/jeeflow/` 找根因
3. 修复: 修改引擎, 分配 FIX-T 编号
4. 测试: 写 BDD 防止回归
5. 标记: 在 `docs/BUGS.md` 记录
6. 通知: 见 §3.5

#### 子流程 B · improve (改进建议)

1. 评估: 是否在 `FREEZE.md` 范围外
2. 排期: 入 `ROADMAP.md` Phase X.Y
3. 或拒绝: 解释理由, 告诉客户

#### 子流程 C · doc (文档问题)

1. 定位: `docs/` 哪一份哪一节
2. 修改: hermes 直接改 (本阶段唯一允许修改 docs/ 的场景, 见 §6 例外条款)
3. 同步: 在 PR 中注明反馈编号
4. 通知: 见 §3.5

#### 子流程 D · UX (UI / 体验)

1. 收集: 场景 + 痛点 + 期望
2. 转 UI: 写入 `ui/` 需求池 (不直接改, 留给 UI 团队)
3. 排期: UI 团队决定

#### 子流程 E · consult (咨询)

1. 即时回复 (Slack / 飞书)
2. 沉淀: 若高频, 写入 FAQ
3. 通知: 复制对话存档

**处理产物**: 更新 `FB-NNNN.json`, 添加处理记录 + 处理人 + 进度.

---

### 3.4 步骤 04 · 验证

**两层验证**:

#### 4.1 内部验证

| 类型 | 验证方法 |
|------|----------|
| bug | BDD 新用例 PASS, 双端 (8101 + 8102) 一致 |
| improve | 客户场景复现成功 |
| doc | 客户场景对照文档可执行 |
| UX | UI 截图 / 视频确认 |

**验证产物**: `FB-NNNN.json` 添加 verification 字段 (时间 + 方式 + 结果).

#### 4.2 客户回访

**回访方式**:
- 客户同意时: 直接发改进后的截图 / 文档
- 客户未回应: 异步通知, 等候确认
- 客户不满意: 回到步骤 03 重新处理

**回访失败处理**:
- 7 天未回应 → 邮件再发一次
- 14 天仍未回应 → 标记"已通知, 客户沉默", 但闭环视为完成
- 30 天仍无回应 → 归档

---

### 3.5 步骤 05 · 通知

**通知方式** (按客户类型):

| 客户 | 方式 | 时机 |
|------|------|------|
| L3 业务客户 | 飞书 / 微信 / 邮件 | 修复后 24h 内 |
| L2 流程客户 | DM + 文档链接 | 修复后 24h 内 |
| L1 引擎客户 | 邮件 + CHANGELOG | 修复后 7d 内 (随版本) |

**通知内容模板**:

```
【jeeflow 反馈闭环 · FB-NNNN】

你好 {客户名},

你 {日期} 反馈的 "{原问题摘要}" 已处理:

✅ 已修复 (BUG-编号 / FIX-T 编号)
📄 改进说明: {一句话}
🔗 相关文档: {链接}
🧪 验证用例: {BDD 编号}

下次引擎发布时会包含此修复, 时间约 {预计日期}.

感谢你的反馈, 帮助 jeeflow 变得更好.

— hermes (流程设计师) / bro (引擎开发者)
```

**通知产物**: `FB-NNNN.json` 添加 notified 字段 (时间 + 渠道 + 内容).

## 5. 反馈类型 SLA

| 类型 | 首次响应 | 内部闭环 | 客户通知 | 总周期 |
|------|----------|----------|----------|--------|
| bug P0 | 24h | 7d | 24h 内 | ≤ 7d |
| bug P1 | 3d | 30d | 24h 内 | ≤ 30d |
| improve P2 | 7d | 90d 或排期 | 24h 内 | ≤ 90d |
| doc P1 | 3d | 14d | 24h 内 | ≤ 14d |
| UX P2 | 7d | 90d 或排期 | 24h 内 | ≤ 90d |
| consult | 即时 | 当天 | 当天 | ≤ 1d |

**违反 SLA**:
- 每次违反, 在 `metrics/` 记录
- 月底统计, 写入月度报告
- 连续 3 月违反同类型, 触发流程改进

## 6. 例外条款 (重要)

> 本阶段 `FREEZE.md` 禁止修改 raw data 目录. 但反馈闭环是**唯一例外**.

| 例外 | 允许修改 | 不允许 |
|------|----------|--------|
| bug 修复 | `vendor/jeeflow/*.py` + 配 BDD | 其它无关代码 |
| doc 修正 | `docs/*.md` 中事实错误 | 大段重写 |
| SLA 调整 | `sla/check.sh` | 删除已有检查 |
| 反馈登记 | `skills/feedback/inbox/FB-NNNN.json` | 其它 skills 文件 |

**例外触发条件**:
- bug 修复必须有 `FB-NNNN` 引用
- doc 修正必须有 `FB-NNNN` 引用
- 修改后必须通知客户
- 修改必须可在 `git log` 中追溯

**没有 `FB-NNNN` 的 raw data 修改, 一律视为越权, 必须撤销.**

## 7. 反馈指标 (Feedback Metrics)

### 7.1 月度指标

| 指标 | 含义 | 公式 | 目标 |
|------|------|------|------|
| 反馈量 | 月内接收总数 | count | — |
| 闭环率 | 已闭环 / 总数 | closed / total | > 80% |
| P0 SLA 达标率 | 7d 内闭环 P0 / 总 P0 | pass_p0 / total_p0 | 100% |
| P1 SLA 达标率 | 30d 内闭环 P1 / 总 P1 | pass_p1 / total_p1 | > 80% |
| 客户回复率 | 客户确认 / 通知总数 | confirmed / notified | > 50% |
| 重复反馈率 | 同类反馈二次出现比例 | repeated / total | < 10% |

### 7.2 季度指标

| 指标 | 含义 | 公式 | 目标 |
|------|------|------|------|
| 客户 NPS | 季度调研 | NPS 标准 | > 30 |
| Top-3 痛点 | 反馈最多的 3 个问题 | 排序 | 已制定应对方案 |
| 引擎 BUG 数 | 季度新增 BUG | 计数 | 递减 |
| 文档清晰度 | 文档相关反馈占比 | doc_fb / total | < 10% |

### 7.3 年度指标

| 指标 | 含义 |
|------|------|
| 客户留存率 | 年初客户年底仍活跃比例 |
| 客户数增长 | 季度环比 |
| 反馈闭环周期中位数 | 全年中位数 |
| 反馈驱动改进占比 | 经反馈闭环的改进 / 总改进 > 70% |

## 8. 反馈的二次利用

每次闭环的 `lessons_learned` 必须沉淀到:

| 内容类型 | 沉淀位置 | 沉淀人 |
|----------|----------|--------|
| 引擎 BUG | `docs/BUGS.md` | bro |
| 引擎约束 | `docs/known-issues.md` | bro |
| 流程设计反模式 | `docs/flow.md` §X | hermes |
| 文档不足 | 修订对应 `docs/*.md` | hermes |
| UX 痛点 | `ui/requirements/` | UI 团队 |
| 客户洞察 | `skills/customers/<id>.yaml` | hermes |
| 制度漏洞 | `skills/FEEDBACK.md` / `RACI.md` / `ROADMAP.md` | hermes + bro |

**强制**: 任何反馈闭环必须填 `lessons_learned`, 否则视为未闭环.

---

## 9. 反模式 (不要做)

| 反模式 | 为什么错 |
|--------|----------|
| 接收后忘记登记 | 失去追溯 |
| 修复后不通知客户 | 客户不知道, 失去信任 |
| 修改 raw data 不带 FB 编号 | 不可追溯, 视为越权 |
| 把所有反馈当 P0 | 失去优先级 |
| 把"需求"当"BUG" 修 | 范围蔓延 |
| 闭环后不写 lessons_learned | 经验流失 |
| 一问多答, 跳步 | 流程失控 |
| 客户沉默就当满意 | 不严谨, 需主动回访 |

## 11. 与 `users.md` 的关系

`users.md` (历史) 描述**接收**通道, 本文件描述**全闭环**.

| 阶段 | 文档 |
|------|------|
| 接收通道 (怎么问) | `users.md` |
| 全闭环 (怎么做) | 本文件 |
| 数据结构 (怎么记) | 本文件 §4 |
| 指标 (怎么评) | 本文件 §7 |

**注意**: `users.md` 是"如何与 flowuser 对话"的入口约定; 本文件是"对话之后发生什么"的流程设计.
两者不冲突, 是同一系统的两个视图.

## 12. 与 FREEZE.md 的关系

`FREEZE.md` 是总闸, 本文件是例外清单 (§6):
- 接收反馈 → 永远允许

- 处理反馈中, **只有与 FB-NNNN 关联的 raw data 修改允许**
- 通知 / 沉淀 → 永远允许

详见 `FREEZE.md` §6.
