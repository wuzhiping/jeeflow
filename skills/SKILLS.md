## 2. 四个支柱

```
            ┌─────────────────────────────────────────────┐
            │  CUSTOMER.md  (客户是谁 / 旅程地图)          │
            └────────────┬────────────────────────────────┘
                         ↓
   ┌──────────────────────────────────────┐
   │  FEEDBACK.md  (反馈闭环 · 唯一引擎)   │  ← 本轮最核心
   └──────┬─────────────┬─────────────┬───┘
          ↓             ↓             ↓
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ 引擎     │  │ 流程     │  │ 文档     │  ← 三类改进源
   │ (vendor) │  │ (flows)  │  │ (docs)   │
   └────┬─────┘  └────┬─────┘  └────┬─────┘
        └──────────┬──┴─────────────┘
                   ↓
            ┌─────────────┐
            │  ROADMAP.md │  (下一阶段做什么)
            └──────┬──────┘
                   ↓
            ┌──────────────────┐
            │  SKILL-TREE.md   │  (谁来做 / 怎么做)
            │  RACI.md         │  (谁负责 / 谁协作)
            └──────────────────┘
```

**核心关系**:
- 客户是起点 (不是引擎)
- 反馈是引擎 (驱动所有改进)
- 路线图是承诺 (按客户价值排序)
- 技能树 + RACI 是执行机制

## 3. 关键约定

### 3.1 只读目录 (raw data)
下列目录**禁止修改**, 仅作事实查询:

- `vendor/jeeflow/` — 引擎源码 (参考实现)
- `vendor/jeeflow-original/` — 原版对照
- `main.py` / `main_pg.py` / `main_common.py` / `main_meta.py` — 服务入口
- `flows/*.json` — 流程定义 (现状)
- `tdd/*` — 流程验证 (历史)
- `bdd/*` — 引擎回归 (历史)
- `sla/*` — 健康度检查 (历史)
- `docs/*.md` — 文档 (历史)
- `spi/` — 业务嵌入接口
- `ui/` — 前端 (本阶段不输出)
- 根目录 `*.md` — 项目元信息 (历史)
- `statics.json` — 统计快照

### 3.2 唯一可写目录
- `skills/` (本目录) — 制度与技能文档

### 3.3 反查事实的方法
需要确认"引擎是否支持 X" 时:
1. `grep -r "X" vendor/jeeflow/` — 看源码
2. `grep -r "X" docs/known-issues.md` — 看约束
3. `grep -r "X" docs/BUGS.md` — 看已知 BUG
4. `grep -r "X" flows/` — 看用法
5. **不要**凭记忆回答; **不要**捏造 API

### 3.4 命名约定
新文档使用清晰英文文件名, 含义自解释:
- `SKILLS.md` · 索引
- `FREEZE.md` · 冻结
- `CUSTOMER.md` · 客户
- `FEEDBACK.md` · 反馈
- `ROADMAP.md` · 规划
- `SKILL-TREE.md` · 技能
- `RACI.md` · 协作
