# CUSTOMER.md · 客户画像与旅程地图

> 视角: 谁在用 jeeflow, 用它做什么, 在哪些瞬间需要我们.
> 关联: RML §1 角色全景是"内部角色", 本文件定义**外部客户**.
> 用途: 一切改进以本文件的客户画像为锚.

---

## 1. 客户 vs 角色

| 维度 | RML 内部角色 | 本文件客户 |
|------|---------------|------------|
| 视角 | 谁来造 / 维护系统 | 谁来用系统 |
| 数量 | 10 个 (相对固定) | 动态, 取决于业务 |
| 关心 | 工程 / 文档 / 测试 | 价值 / 效率 / 体验 |
| 反馈入口 | RML §4 RACI | `skills/users.md` 通道 |
| 服务对象 | 系统本身 | 业务本身 |

**核心区别**: 内部角色改变系统; 客户**使用**系统产生业务结果.
客户的成功 = jeeflow 的成功.

## 2. 客户三层分类

按"是否直接接触引擎" 分层:

```
┌─────────────────────────────────────────────┐
│  L1 · 引擎客户 (直接消费 API)                │  极少数
│  ├─ 集成开发者                                │
│  └─ 自研工作流系统的工程团队                  │
├─────────────────────────────────────────────┤
│  L2 · 流程客户 (设计 + 运行流程)              │  少数
│  ├─ 流程设计师 (RML 角色 3)                  │
│  ├─ 流程管理员                               │
│  └─ 业务领域专家 (设计分支规则)              │
├─────────────────────────────────────────────┤
│  L3 · 业务客户 (流程的实际使用者)             │  多数
│  ├─ 申请人                                   │
│  ├─ 审批人                                   │
│  └─ 抄送人 / 知会人                          │
└─────────────────────────────────────────────┘
```

### 2.1 L1 · 引擎客户

**特征**:
- 直接调用 `main.py` / `main_pg.py` 提供的 `/wf/{action}` API
- 拥有自己的代码库, jeeflow 是依赖
- 对引擎**行为正确性**最敏感
- 数量极少 (通常 < 10)

**核心需求**:
- API 稳定 + 向后兼容
- 文档齐全 (OpenAPI + 行为说明)
- BUG 修复有 SLA
- 引擎升级不破坏现有集成

**反馈触发**:
- API 返回与文档不符
- 行为差异 (MEM vs PG)
- 性能不达标
- 集成发现的设计缺陷

### 2.2 L2 · 流程客户

**特征**:
- 设计 `flows/*.json` 或同等物
- 配置流程的字段权限 / 会签 / 委托规则
- 不写代码 (或写很少)
- 需要 UI 设计器 (当前依赖 `ui/`)
- 数量较少 (团队规模决定, 通常 1-5 人)

**核心需求**:
- 设计器易用
- 6 种节点 (task / decision / fork / join / custom / end) 表达力够
- 字段权限 / 会签模式覆盖真实场景
- 变量命名 / submitType 有规可循
- 流程测试方便 (实例化 / 调试)

**反馈触发**:
- 节点选型不足 (场景无法表达)
- 字段权限规则表达不全
- 会签模式不够 (需要新增)
- 测试难 (无法复现 / 无法定位)
- 文档含糊 / 自相矛盾

### 2.3 L3 · 业务客户

**特征**:
- 多数用户 (单位: 数十到数万)
- 通过 UI (飞书 / 微信 / Web) 操作
- 不会写 JSON, 不会调 API
- 关注"我的申请能否尽快通过"
- 数量: 视业务规模

**核心需求**:
- 通知及时 (不漏)
- 界面清晰 (字段含义明白)
- 操作简单 (3 步内完成)
- 移动端可用
- 委托方便 (出差 / 休假)
- 进度可见 (在哪一步了)

**反馈触发**:
- 通知不到 / 通知太晚
- 字段含义不清楚 (填错被打回)
- 找不到入口
- 移动端体验差
- 委托后对方看不到待办
- 看不到流程进度

## 3. 客户旅程地图 (Customer Journey)

### 3.1 L3 业务客户 · 6 阶段旅程

```
   阶段1         阶段2         阶段3         阶段4         阶段5         阶段6
 认知/启动 → 提交申请 → 等待审批 → 参与审批 → 收到结果 → 复盘/续办
   "听说"     "填表"      "等待"      "同意"      "完成"      "再办一次"
```

| 阶段 | 客户行为 | 触点 | 痛点 (常见) | 我们的改善点 |
|------|----------|------|-------------|--------------|
| 1. 认知/启动 | 收到飞书/邮件通知 | 通知 | 通知错过 / 找不到入口 | 通知策略 · 入口统一 |
| 2. 提交申请 | 填字段 + 上传附件 | 表单 | 字段含义不清 / 必填项漏 | 字段说明 · 默认值 |
| 3. 等待审批 | 被动等待 + 催办 | 进度页 | 不知当前节点 / 催办无门 | 进度可见 · 催办入口 |
| 4. 参与审批 | 看上下文 + 决策 | 审批页 | 上下文不全 / 字段误读 | 审批页信息密度 |
| 5. 收到结果 | 同意 / 拒绝通知 | 通知 | 结果滞后 / 链接失效 | 结果通知即时 |
| 6. 复盘/续办 | 二次申请 / 续办 | 历史 | 历史难查 / 续办重新填 | 复用上次内容 |

### 3.2 L2 流程客户 · 5 阶段旅程

```
   阶段1         阶段2         阶段3         阶段4         阶段5
 需求理解 → 流程设计 → 流程测试 → 上线发布 → 运营优化
   "业务要     "画图"      "跑通"      "上线"      "看数据"
    什么"
```

| 阶段 | 行为 | 痛点 | 我们的改善点 |
|------|------|------|--------------|
| 1. 需求理解 | 与业务方对话 | 需求不清晰 / 边界模糊 | 设计访谈清单 |
| 2. 流程设计 | 画图 + 写 JSON | 节点选型困惑 · 字段权限写错 | 设计 checklist |
| 3. 流程测试 | tdd + 跑实例 | 复现难 · 状态看不懂 | 实例固化模板 |
| 4. 上线发布 | 部署到生产 | 双端不一致 · 性能差异 | 部署前自检 |
| 5. 运营优化 | 看 SLA + 反馈 | 不知问题在哪里 | 反馈通道入口 |

### 3.3 L1 引擎客户 · 4 阶段旅程

```
   阶段1         阶段2         阶段3         阶段4
 集成接入 → 上线运行 → 监控运维 → 升级扩容
   "跑通"      "稳定"      "健康"      "扩"
```

| 阶段 | 行为 | 痛点 | 我们的改善点 |
|------|------|------|--------------|
| 1. 集成接入 | 读 OpenAPI + 写适配 | 文档不全 / 行为不明 | OpenAPI 完善 |
| 2. 上线运行 | 跑日常业务 | BUG 难定位 | trace_id 体系 |
| 3. 监控运维 | 看 metrics + 日志 | 监控盲区 | metrics 覆盖 |
| 4. 升级扩容 | 升级引擎 / 加节点 | 兼容性问题 | 升级文档 + 双端一致 |

## 4. 客户成功指标 (Customer Success Metrics)

> 客户成功 ≠ 引擎稳定. 客户成功 = 客户的目标达成.

### 4.1 L3 业务客户

| 指标 | 含义 | 目标 |
|------|------|------|
| 平均审批时长 | 提交 → 终态 | < 24h (P95) |
| 通知到达率 | 应到 / 实到 | > 99% |
| 一次通过率 | 不被打回 / 总提交 | > 80% |
| 移动端使用占比 | 移动审批次数 / 总审批 | > 40% |
| 客户满意度 (NPS) | 季度调研 | > 30 |

### 4.2 L2 流程客户

| 指标 | 含义 | 目标 |
|------|------|------|
| 流程设计周期 | 需求 → 上线 | < 3 工作日 (简单流程) |
| 流程 BUG 率 | 上线后 BUG / 总流程 | < 5% |
| 设计器使用率 | UI 设计 / 总设计 | > 70% |
| 自助解决率 | FAQ + 文档解决 / 总问题 | > 60% |

### 4.3 L1 引擎客户

| 指标 | 含义 | 目标 |
|------|------|------|
| API 调用成功率 | 200 / 总调用 | > 99.9% |
| 双端一致性 | MEM 与 PG 行为一致率 | 100% |
| 集成 BUG 修复 SLA | 反馈 → 修复 | P0 ≤ 24h, P1 ≤ 7d |
| 文档完整度 | OpenAPI 覆盖 action | 100% |

## 6. 客户优先级排序原则

| 优先级 | 客户类型 | 理由 |
|--------|----------|------|
| P0 | L3 业务客户 (高频使用) | 影响最大人数, 失败最直观 |
| P1 | L2 流程客户 (设计新流程) | 流程上线后产生 L3 客户 |
| P2 | L1 引擎客户 (集成方) | 数量少但单客价值高 |

**冲突解决**: 当 L1 与 L3 需求冲突时, **L3 优先**.
理由: L3 数量大, L1 可通过配置 / 文档缓解.

## 8. 与 RML 的对照

| RML 角色 | 对应客户层 | 关系 |
|----------|-------------|------|
| 角色 1 引擎开发者 | 服务 L1 | 上游 |
| 角色 2 引擎测试 | 服务 L1 | 上游 |
| 角色 3 流程开发者 (hermes) | 既是 L2 也是对接桥梁 | 关键 |
| 角色 4 流程测试 | 服务 L2 | 上游 |
| 角色 5 业务审批人 | L3 业务客户 | 服务对象 |
| 角色 6 架构师 | 服务所有层 | 上游 |
| 角色 7 SRE | 服务 L1 + L3 | 上游 |
| +A 培训师 | 服务 L3 | 上游 |
| +B 审计 | 服务 L3 监管 | 上游 |
| +C 集成开发者 | 是 L1 客户 | 服务对象 |

**关键洞察**: 角色 5 (业务审批人) 既是我们的内部角色, 也是 L3 客户的典型代表.
两者重合度高, 这是 jeeflow 私用项目的特殊性, 但对外推广时必须分开.
