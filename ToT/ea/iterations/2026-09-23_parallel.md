## 2. 设计

### 2.1 并发模型
```python
sem = asyncio.Semaphore(args.parallel)

async def run_with_sem(sc):
    async with sem:  # 限流
        return await run_path(...)

results = await asyncio.gather(*[run_with_sem(sc) for sc in scenarios])
```

- `args.parallel = 1`：串行（原行为）
- `args.parallel = N`：最多 N 个 scenarios 同时跑

### 2.2 为什么 in-memory engine 加速不明显？
- MemoryRepository 是单线程 asyncio loop
- scenarios 之间没有真正的 CPU bound 阻塞
- 加速主要在 I/O bound 场景（如真实 HTTP 调用）
- 当前测试数据少，所以加速有限

### 2.3 何时会显著加速？
- 多个 scenarios + 复杂流程（每个 5+ 步）
- 真实 HTTP 调用引擎（main_pg.py + remote）
- 大量 scenarios（10+）
- 异步副作用（数据库写入、外部 API 调用）

## 7. 经验沉淀

### 7.1 并发 vs 串行选择
| 场景 | 推荐 |
|------|------|
| 调试单个 scenario | 串行 |
| CI 完整回归（in-memory）| 串行（足够快）|
| CI 完整回归（remote engine）| 并发 3-5 |
| 大量 scenarios（10+）| 并发 5-10 |
| 实跑 + baseline 对比 | 并发 3（节省时间）|

### 7.2 注意事项
- ⚠️ in-memory engine 并发收益有限（实测 < 5%）
- ⚠️ 共享 facade（无状态），可以安全并发
- ⚠️ scenarios 之间无依赖（各自独立 instance），并发安全
- ⚠️ results 字典并发写入（Python GIL 保护，但保险起见用 gather 顺序处理）
