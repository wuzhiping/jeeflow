## 3. 教训（What Worked / What Didn't）

### 3.1 ✅ 做得好的

| # | 实践 | 价值 |
|---|------|------|
| 1 | **协议先行**（Decision Mem v1.0 lite 落地后才写代码） | 协议稳定 → 引擎改动最小 |
| 2 | **文档与代码同步**（每次 baseline 都更新 INDEX + README） | 可追溯性 |
| 3 | **自动化留痕**（每次操作都写留档文件） | 合规 + 复盘便利 |
| 4 | **三环境一致**（local dev 8101/8102 ↔ customer abc.feg.cn） | 部署平滑 |
| 5 | **飞轮定位**（`ea/` 不是工具是飞轮） | 主动沉淀 |

### 3.2 ⚠️ 待改进的

| # | 问题 | 教训 | 写入哪里 |
|---|------|------|----------|
| 1 | v0.5 的 5 阶段线性骨架有 W012 BUG | 早期应先用 `tdd-flow.py` 验一遍再决定结构 | §8.4 度量指标 |
| 2 | 角色映射 R3 → fdep_rml → u_fdp_pm 走了 3 步 | 应直接占位简化（v0.5 → v0.6 → v0.6.1） | §5 Pattern 5（baseline 演化） |
| 3 | customer-data-reset SOP 是事后补的 | 第一次 reset 后才意识到需要 SOP | §6.3（操作类 SOP）|
| 4 | 客户服务器第一次 reset 没做 smoke test | 后加 §6.4 "冒烟跑到底" | §6.3 customer-data-reset |
| 5 | README 顶部摘要在迭代中容易失修 | 必须每次新增产物时同步 | README §0 演进原则 |

### 3.3 🔁 本次迭代的最大资产

- **Job Card + Decision Mem + Pickup API 三件套** → 把"executors 接力不丢上下文"从概念变成可落地协议
- **审计链路**（job_card_url） → 让任意历史 instance 都能回查"哪张卡引导了哪个决策"
- **ea/roadmap.md**（飞轮） → 把本次迭代的所有方法论沉淀为可复用资产

## 7. 给下个迭代记录的建议

1. **格式对齐**：本文件结构（时间线 / 转折 / 教训 / 数据 / ADR / 预测）作为模板
2. **数字必须真实**：从 baseline / 目录 / 留档实际数，不要估算
3. **教训要有行动**：每个 "⚠️" 项必须指向"已写入 roadmap.md §X"（不写入等于没学）
4. **ADR 量化**：每个决策记录"选项 / 选择 / 理由 / 落地位置"
