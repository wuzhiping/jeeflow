# ToT/docs/_meta/layering.md · 文档体系 3 层定位模型

> **变更原因（v3.9，2026-09-26）**：随着系统从「初创期」进入「服务治理期」，doc 体系也需要分层明确职责。本文件为这一模型的事实声明。
>
> **广而告之**：所有协作者（人 / AI）应当据此理解「在哪一层写文档」+「去哪一层查文档」。

---

## 0. 一句话模型

```
docs/        初创期 · 落地指南 · 一次性
ToT/         服务治理期 · 基本准则 · 持续运行
ToT/docs/    初创期的相关外部文档的引入、修正 · 半永久资产
```

---

## 1. 三层定义

### Layer 1 · `docs/`（项目根）

| 维度 | 内容 |
|---|---|
| **时期定位** | **初创期 · 落地指南**（系统从 0 到 1 的阶段） |
| **作用** | 教新来者"如何把系统跑起来" / "如何对接 SPI" / "如何写 processDefine" |
| **读者** | 新加入的开发者 / AI Agent（首次接触） |
| **生命周期** | 一次性：系统进入治理期后逐渐沉淀到 ToT/ |
| **特点** | 偏「how-to」· 偏「上手即用」· 入口导向 |

**典型文档**：
- `docs/architecture.md`（引擎整体架构）
- `docs/api.md` / `docs/actions.md` / `docs/openapi.json`（HTTP 端点）
- `docs/flow.md`（流程 JSON 完整规范）
- `docs/AGENTS.md`（AI 协作指南）
- `docs/known-issues.md`（§1-§78 引擎行为约束）

---

### Layer 2 · `ToT/`（治理期）

| 维度 | 内容 |
|---|---|
| **时期定位** | **服务治理期 · 基本准则**（系统进入生产运行后） |
| **作用** | 持续运营 / 持续改进 / 持续协作的工作机制 |
| **读者** | 全员（流程设计者 / 开发者 / 部署运维 / 知识管理员） |
| **生命周期** | 持续运行：每次迭代都更新 |
| **特点** | 偏「governance」· 偏「how we work」· 角色+流程导向 |

**典型文档**：
- `ToT/GETTING_STARTED.md`（新人 5 分钟入门）
- `ToT/HANDBOOK.md`（知识手册）
- `ToT/README.md`（工作规范）
- `ToT/ea/roadmap.md`（EA 飞轮架构）
- `ToT/sop/*.md` + `*.py`（操作 SOP + 自动化脚本）
- `ToT/flows/fdep/`（蓝本制品）
- `ToT/CC/`（客户中心 4 persona）

---

### Layer 3 · `ToT/docs/`（初创期外部文档的引入修正）

| 维度 | 内容 |
|---|---|
| **时期定位** | **初创期的相关外部文档的引入、修正**（上游 jeeflow 文档的本地化裁剪） |
| **作用** | 把上游 `jeeflow-doc.mldong.com` 的 6 语言版本裁剪为本仓单语言；保留设计契约 + 本仓实测 |
| **读者** | 任意角色遇到术语 / API / 设计原理疑问时 |
| **生命周期** | 半永久：上游有变更时同步；本仓有改进时同步 |
| **特点** | 偏「reference」· 偏「契约」· 单语言/单版本 |

**典型文档**：
- `ToT/docs/guides/`（9 篇用户指南）
- `ToT/docs/spec/`（11 篇规范契约）
- `ToT/docs/concepts/`（10 篇设计原理）
- `ToT/docs/manual/`（11 篇端到端操作）
- `ToT/docs/patterns/`（5 个本仓典型模式）
- `ToT/docs/diffs.md`（与上游 95+ 项差异审计）

## 3. 何时写入哪一层

| 场景 | 写入层 |
|---|---|
| 新人入职：「怎么跑起来？」「HTTP API 在哪？」 | **docs/** |
| 流程设计：「JSON 节点字段是啥？」 | **docs/flow.md** + **ToT/docs/spec/** |
| 「如何发布一个流程？」「如何改流程 JSON？」 | **ToT/sop/** |
| 「客户系统部署怎么操作？」「监控怎么配？」 | **ToT/CC/**（运维 persona）+ **ToT/sop/** |
| 「设计原理是什么？」「为什么这么设计？」 | **ToT/docs/concepts/** |
| 「这个 API 怎么用？签名是啥？」 | **ToT/CC/api-index.md** + **ToT/docs/spec/** |
| 「本仓改了什么？与上游差异？」 | **ToT/docs/diffs.md** |
| 「飞轮怎么转？」「roadmap 当前状态？」 | **ToT/ea/roadmap.md** |
| 「客户场景故事 / 季度回顾 / E2E 演示」 | **ToT/CC/_stories/** |

## 4. 演进原则

### 4.1 docs/ → ToT/ 的迁移

当 `docs/` 中的内容沉淀为「持续运营知识」（如：跑了一次 reset 后发现新坑，需要 SOP），应迁移到 `ToT/sop/` 或 `ToT/ea/`。

### 4.2 ToT/docs/ 的裁剪原则

每篇 `ToT/docs/*.md` 必须包含 4 段元数据：

1. **来源**（`> 来源：https://jeeflow-doc.mldong.com/...`）
2. **定位**（读者角色 + 用途）
3. **本仓实测**（代码位置 / 行号 / 类名 / 签名）
4. **裁剪记录**（哪些上游章节保留 / 裁掉 / 重写）

### 4.3 严禁

- ❌ 把上游未裁剪的 6 语言版本直接复制到 ToT/docs/
- ❌ 把 ToT/ 治理类文档写到 docs/
- ❌ 把客户故事（一次性演示）放到 ToT/docs/（应放 ToT/CC/_stories/）

---

## 5. 与 release.sh 的关系

`ToT/sop/release.sh` 在每次发布时：
1. ✅ 自动更新 `vendor/jeeflow/__init__.py:__version__`（当 git diff 含代码变更）
2. ⚠️ **人工确认**（当 git diff 仅含文档变更时）—— 见 `ToT/sop/version-bump-guard.py`

**原则**：`__version__` 反映运行时行为变化。文档变更不应自动 bump 引擎版本号。

详见 `ToT/sop/version-bump-guard.py` 的 `--help`。
